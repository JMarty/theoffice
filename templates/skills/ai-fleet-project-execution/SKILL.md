# AI Fleet Project Execution

## When to use

A user hands over a project with a "see it through as a team, autonomously" instruction. Triggers:
- "I'm leaving it to you, get it done"
- "Keep giving the agents tasks", 
- "I don't want to interfere, just send me the weekly report"

## KANBAN-FIRST workflow (MANDATORY default)

Every project and subtask is MANDATORILY managed through a kanban card. Ad-hoc inter-agent message-only delegation is for EMERGENCIES only (e.g. broken-prod fix, time-critical pairing) -- everything else:

1. **Subtask → new card**: with project field, assignee field (backend dev / marketing / video agent / etc.), priority + status='planned' or 'in_progress'.
2. **Delegation → inter-agent message + kanban reference**: in the message, reference the card ID (`See kanban card XXXX, status=in_progress`). The agent should also report back on the card (write a comment into the `kanban_comments` table).
3. **Sub-agent obligation**: built into the agent's CLAUDE.md, that it UPDATES STATUS on every task (planned → in_progress → waiting/done). NOT just an inter-agent reply.
4. **Orchestrator 3-4 hour audit**: a scheduled task that runs every 3 hours and:
   - Cleans up 7+ day old done cards (archive)
   - Calls the assignee to account via inter-agent message for stuck tasks (>24h in_progress without movement)
   - Flags new unassigned/delegation-less cards to the orchestrator
5. **Weekly report**: the orchestrator summarizes the board state to the user on Telegram (every Friday).
6. **Meta-tasks do NOT go on the kanban**: anything that is a continuous monitor / scheduled-task / permanent `/loop` cycle (e.g. "GitHub PR monitor", "Morning kickoff") should not be a kanban card -- because the kanban audit will mark it as stuck. Keep these in a `~/.claude/scheduled-tasks/<name>/` folder, or in `~/.claude/scheduled-tasks.json`. (Based on sub-agent feedback: PR watching is handled by a scheduled-task, not a kanban card.)

## Procedure

### 1. Kickoff (~30 minutes)

1. **Kanban parent card**: create a big hierarchy-tree parent card for the project. Description: scope, goals, rules.

2. **Sub-cards**: break the project down into a per-agent subtask list. Convention: `<project>m###` (orchestrator marketing coordination / DNS / weekly report), `<project>s###` (backend dev), `<project>n###` (urgent crash targets), etc. Each sub-card: assignee, priority, description, sort_order.

3. **Inter-agent kickoff**: send a detailed task list to the agents via inter-agent msg. Separately to the marketing agent (business/marketing) and the backend dev agent (technical/development). Brief both sides, and warn them that it is NOT auto-pull (the agent only works when you ping it).

4. **Weekly report scheduled task**: create `~/.claude/scheduled-tasks/<project>-weekly-report.md` with a cron report sender. Friday 17:00, kanban status + agent progress.

5. **HOT memory**: save the current state of the project (parent + sub card IDs, scope, deadlines).

### 2. Ongoing coordination

- **Inter-agent msg = task delegation**, **kanban = state tracking**. Neither works without the other.
- **On every agent report**: 1) Update the kanban card (status, comment), 2) Inter-agent acknowledgement + next task, 3) Telegram update to the user ONLY if a decision is needed from them or it is an important milestone.
- **Parallel tasks**: if an agent has no blocked task, do NOT wait, give it a proactive "if you're bored" task (competitor analysis, README docs, etc.).
- **Brief revisions**: make every review concrete (a 1, 2, 3 point list of what to change). Not a general remark ("I don't like it"), give concrete string replacements.

### 3. Handling stack pivots

The user often pivots the architecture based on a passing idea. When reacting to pivots:

1. **Kanban update**: add pivot info (what we switched to and why) as a comment on the parent + affected sub cards.
2. **Inter-agent msg**: re-brief the agents with the changed scope. Do NOT throw away work done AFTER the pivot, port / reuse as much as possible (usually 90% of the code survives).
3. **Decision log memory** (cold tier): record the pivots with timestamps.
4. **Time estimation**: do not estimate in human-hours (the user explicitly corrected this). AI pace is ~5-10x faster than a human developer. 8 hours of work = 1 hour at AI-fleet pace.

### 4. Handling deploy blockers

The fleet cannot register a Cloudflare/Netlify/Stripe account, because:
- computer-use Chrome tier=read (clicking is blocked)
- There is generally no claude-in-chrome MCP
- Account creation is not supported through an API

So deploy blockers always wait on the user. Mitigation:
- **Bundle the requests into one Telegram msg** (CF token + Account ID + Netlify connect + DNS CNAME = one message, the user does it in 5-10 minutes).
- **Consider simplifying the stack**: if the architecture can be reduced to Supabase-only (Edge Functions = Worker proxy equivalent for an MVP), drop Cloudflare entirely. One vendor = one deploy blocker.

## Pitfalls

- **When delegating research, EXPLICITLY demand source labeling and a recent time period.** A research sub-agent by default tends to build on older data points and give estimates for the current period. Solution: in the brief, EXPLICITLY: 1) 'Focus on fresh data: <specific period>'. 2) 'Source label for every number: [FACT] vs [estimate] vs [NOT PUBLIC]. Estimate only if there is really no public data.' 3) When delegating HTML/presentation, have it visually distinguish the 3 categories with badges (green/amber/grey).

- **Video/asset render: a visual watch-check is mandatory before finalizing.** After a video render, do NOT settle for playing the mp4 once -- check in watch-mode (live preview) or frame-by-frame at the critical moments (stagger-peak, spring-back overshoot frame, animation peak). UI elements (card, chip, badge) must always stay within the layout bounds. When delegating, the brief should contain: 'AFTER rendering, check in watch-mode or frame-by-frame that no UI element overhangs the container bounds.'

- **When delegating to an asset-producing sub-agent, EXPLICITLY add 'send it on Telegram as an attachment'.** Asset-producing sub-agents tend to report back only the file path on the inter-agent message, and the user does NOT receive the actual file. The correct brief rule: 'When X is done → send it to the user on Telegram (<user-chat-id>), attached with the reply tool files: argument, with a short caption.' It should always be in the brief.

- **MCP disconnect: do your own reconnect with tmux send-keys.** The orchestrator runtime's tmux pane (check with `tmux display-message -p '#S'`) is reachable with send-keys. Sequence: `tmux send-keys -t <orchestrator-session> "/mcp"` + Enter → wait 1-2s → arrow navigation (Up/Down) to the target server (Telegram MCP is near the end of the list in the Built-in MCPs section; check the `❯` cursor with capture-pane) → Enter (select) → Down → Enter (Reconnect). After 3s capture-pane shows the "Reconnected to plugin:" success string. **Do NOT use /mcp as a Skill tool or bot command** -- it REALLY gets dismissed ("MCP dialog dismissed" log) and reaches nothing. (The feedback_mcp_reconnect memory details the 8-step procedure.)

- **Don't send duplicate reviews**: if the sub-agent signals "same commit, already merged"/"it was a duplicate review", do NOT start another review agent. Compare the HEAD commit hash with the already reviewed one -- if they match, stop. Solution: before review `gh pr view N --json headRefOid` + keep the already reviewed hashes in memory.

- **Auto-pull illusion**: the agents do NOT pull the kanban. They only work when you ping them via inter-agent msg. If you put the thread down for 30 minutes, everyone stops. The scheduled-task auto-ping idea results in a cluttered msg flow (1 agent effectively does 1 task/iteration).

- **Time estimates in human-hours**: the user explicitly corrected that "AI is not human, much faster". Estimation ratio: human 8 hours = AI fleet ~1 hour (in intensive focus). Not "1-2 days" but "2-3 hours of concentrated work". If you overestimate, the user will correct you.

- **Even more precise time bands by task size (calibration)**: 
  - **Micro-task (single-file refinement, small parameter change, SVG attribute swap)**: AI pace **1-3 minutes**. E.g. logo letterform iteration, each 1-2 minutes. Don't say 30-60 minutes, because the user corrects ("I think it's much faster than that").
  - **Small task (rewriting a function, a compact PR)**: AI pace **5-15 minutes**.
  - **Medium task (feature touching several files, writing a new connector from a pattern, adapting an MCP server)**: AI pace **30-90 minutes**.
  - **Large task (new architecture, stack pivot, full OAuth flow + Magic link UI)**: AI pace **2-4 hours** intensively.
  Use these bands for estimates, NOT human-hour extrapolation.

- **A stack pivot is never wasted work**: don't take the user's pivots as an insult. 90% of earlier work is portable (code is architecture-independent, encryption is WebCrypto-native, OAuth handler is runtime-independent). Only the deploy target changes.

- **Computer-use Chrome tier=read**: you CANNOT register accounts on Cloudflare/Netlify/etc. automatically. Don't promise "I'll do it right away" -- instead cleanly delegate the 30-60 second UI flow to the user. Or if a Claude-in-Chrome MCP is installed, try through that.

- **Minimal Telegram noise**: don't send the user a Telegram for every agent update. The weekly report + decision-request moments are enough. A review acknowledgement does NOT go to Telegram, only inter-agent.

- **Multiple agents racing**: if several agents would start on the same task, stop it with an explicit rule in CLAUDE.md. (E.g. the prior incident: one agent started an OAuth workaround flow that another agent also tried.)

- **After a PR squash-merge the child PR becomes CLOSED+CONFLICTING**: if PRs are stacked (PR #1 on the feature/A branch, PR #2 on feature/B where B=A+commits), then after PR #1 is squash-merged into main it automatically **deletes** the feature/A branch (with the `--delete-branch` flag), which destroys PR #2's base -> CLOSED + CONFLICTING. The GitHub UI does not meaningfully support changing the base target in this situation. Solution: locally rebase the feature/B branch onto the updated main (`git rebase main`, skips the duplicate commits via skipped-cherry-pick), force-push with a new branch name, new PR with base=main.

- **gh pr create 504 timeout**: the GitHub GraphQL API occasionally gives a 504 Gateway Timeout. Simply retry after 3-5 seconds, it usually succeeds. Don't double-create -- check `gh pr list --repo X --state open` first to see whether it was already created.

- **Review rule for multi-PR delegation: the orchestrator reviews EVERY PR**: when a big feature breaks into 5+ PRs and you delegated to sub-agents, the user's explicit rule: "YOU always do the reviews". The sub-agent must not merge its own PR, no auto-merge, no "the user will review it" assumption. **Pattern**: (1) sub-agent opens PR, (2) pings inter-agent: "PR X ready for review: <url>", (3) orchestrator `gh pr diff` + local build/test, (4a) IF OK: orchestrator merges + ping "merged, PR Y can start", (4b) IF a fix is needed: exact comment feedback (numbered issue list, marked "medium severity / critical"), sub-agent fix, ping again. The LOW-risk-automatic-merge rule below REMAINS valid for main-stream PRs (single-author sub-agent independent bugfix), but in the case of MULTI-PR DELEGATION the orchestrator always reviews. Reason: the user's specific request for multi-PR features is that nothing slips through without review.
  - **A local tsc build is MANDATORY for PRs on the orchestrator repo** (the prior incident): the backend dev agent's "tests PASS" claim can be MISLEADING -- e.g. a channel-monitor generalization left a shorthand-orphan reference in a logger.info, which caused a `tsc` build failure during the daemon restart, AND THE PORT DIED, dashboard outage for 5+ minutes. Sub-agent testing looks at the specific test file being green, but that is NOT a full build check. **Orchestrator rule**: for orchestrator-repo PRs ALWAYS run `npx tsc` yourself at review time (NOT just the sub-agent's claim), BECAUSE if there is a bug in it and you merge it, the daemon crashes on YOUR side, and that causes an OUTAGE in the whole fleet orchestration. Plus: AFTER a PR merge the explicit `npx tsc && launchctl kickstart -k gui/$(id -u)/com.<service>.dashboard` pattern (build + daemon restart) -- do NOT do a kickstart ad hoc before the build, because the daemon runs from `dist/index.js` and a corrupt dist causes an outage.

- **ClaudeClaw SINGLE-INSTALL architecture clarification** (a standing correction): The ClaudeClaw model is a SINGLE install, NOT client-server. The orchestrator install RUNS ON THE SANDBOX RUNTIME (orchestrator daemon + agents/* + dashboard). The user is a remote user, does NOT run a separate install -- they talk to the orchestrator via TELEGRAM and also view the dashboard on the orchestrator hostname (localhost:3420 in their browser, tunneled to the orchestrator sandbox runtime). **Pattern correction**: IF in the future you suggest machine configuration or install operations to the user (`cd ~/... && git pull` type commands), that is a MISTAKE -- the user has no CLI access, CANNOT run bash commands. Every install / build / daemon restart / git operation must happen on the orchestrator runtime (sandbox runtime), and the user experiences the result of the change in the dashboard / Telegram UI.

- **PR-merge permission: judgment-based, NOT mandatory for every PR**: the user's explicit feedback "if it's OK from your side, do the merge" -- merge proactively if:
  - A sub-agent finished a PR, build OK
  - The diff is clear, low risk (UI bugfix, copy update, content tweak)
  - No irreversible effect (not a migration, not prod-data, not money-flow)
  → MERGE AUTOMATICALLY, just send the user an update message that it is merged.
  
  ASK the user BEFORE merging if:
  - DB migration (irreversible schema change)
  - Production-affecting (money-flow, user-credits, encrypted credentials)
  - Architecture pivot (new feature scope, price change, branding)
  - Stack PR (several dependent PRs on each other, order-sensitive)
  - Uncertainty in the PR diff
  
  Reason: being overly cautious and "asking permission for every PR" slows down fleet throughput. The user wants high-confidence routine UI/copy fixes passed through faster.
  
  How to apply: after every PR create, a quick mental risk check (low/medium/high). LOW = merge automatically + status update. MEDIUM/HIGH = ask. The PREVIOUS rule ("never chain") REMAINS for the `&&` bash command (because in a single tool call it is too fast, the user cannot interject) -- but a `gh pr create` + wait + `gh pr merge` separated at the tool-call level is allowed for a LOW-risk PR.

- **MVP-phasing suggestion: ASK first, don't make an assumption**: when proposing a new feature, do NOT assume the user wants MVP-first / phased rollout. Pattern: when proposing a new feature scope, calculate the plan with the full scope. If you want some feature later, ASK: "Should I start with an MVP (X tool first pass) or go straight to the full scope (X+Y all together)?" Don't decide the scope yourself (the user is revenue-focused, and often likes full functionality on the first go). How to apply: in a kanban plan for a new feature/connector/integration, the default assumption should be full scope, and only suggest an MVP if the concept is obviously too large.

- **SQLite multi-line INSERT in a bash string is fragile**: `sqlite3 db "INSERT ... VALUES (..., 'multi-line description...')"` through a bash string tends to break on the escaping of `'` and `"`, the RETURNING clause, or a quoted description. Pattern: if there is a 2+ line INSERT or a long string, IMMEDIATELY use a temp .sql file + redirect, NOT a bash string. How to apply: when creating a kanban card or any SQL that also contains a description/long-text field, default to the Write tool + .sql + sqlite3 redirect combo.

- **Hungarian accent loss in agent text**: when an agent (especially the backend dev agent, and sometimes other sonnet models) writes Hungarian string constants into code (e.g. translations.ts), it OFTEN strips the accents ("Hogyan mukodik" "Korai hozzaferes" etc.). This is not TUI encoding, it is model output-level ASCII-fying. Mitigation: explicit instruction in the inter-agent msg "copy WITH ACCENTS from the marketing agent's HU copy, do NOT write it in your own words". Verify: after deploy grep the output for typical accented words (`működik`, `hozzáférés`, `támogatás`, `hívás`, `Árak`, `Belépés`). If missing, a fix PR with a full rewrite of the translations. **Regression**: the backend dev agent ASCII-fied AGAIN, because I did not write an EXPLICIT "WITH ACCENTS" warning into the inter-agent msg (I only copied in the marketing agent copy bullets). Reinforced pattern: in EVERY inter-agent msg that asks for a Hungarian UI/copy implementation, the warning "ALL HUNGARIAN TEXT WITH ACCENTS!" is MANDATORY. **Third recurrence** (email templates: confirm-signup, magic-link, reset-password all ASCII-fied) -- the error EXTENDS to every Hungarian HTML/string asset (NOT only i18n files like `translations.ts`), e.g. **email body HTML, marketing copy markdown, scheduled-task SKILL.md, system prompt template, install-script echoes**. **Pragmatic mitigation**: if the error is discovered in the post-merge-pre-apply phase, a double decision: either send the sub-agent back to fix it (slow, the cleaner path per the multi-PR review rule), OR you fix it yourself with sed and force-push to the PR branch. Pragmatic choice: for <100 sed replacements you do it (faster, 5 minutes), for >100 replacements or structure-affecting changes the sub-agent.

- **Dashboard feature implementation: specify mock vs real data FIRST**: for a new dashboard page task the sub-agent by default puts MOCK data in the UI. If real data is needed, specify EXPLICITLY in the inter-agent msg:
  - "Data source: backend endpoint X (or create it if it doesn't exist yet)"
  - OR "mock is OK in the FIRST iteration, the real backend will be a separate kanban task"
  If the backend endpoint doesn't exist yet (analytics API etc.), THAT must be delegated first → BACKEND PR → then the frontend can use it. Pattern: a dashboard-feature task is 2-phase: (1) backend endpoint + schema, (2) frontend page + chart from the endpoint.

- **For a new dashboard page always copy the existing auth-guard pattern**: new pages FIRST flashed the login screen AND redirected to the default page after login (did not stay on the original URL). Cause: the auth-guard logic and redirect target were hardcoded. Solution: EXPLICITLY instruct the sub-agent in the inter-agent msg to copy the existing auth pattern + use a post-login `?next=` parameter (current path).

- **Netlify production branch != main detection**: the Netlify dashboard Production branch setting for the repo can DRIFT from main to a feature branch. Symptom: you merge PRs to main, the dashboard does not show the fresh code. It can only be changed in the Netlify dashboard (Site config → Build & deploy → Continuous deployment → Branches), NOT in the repo's netlify.toml. Verify pattern: extract the MAIN sha with `gh api repos/.../commits/main -q .sha` + the Netlify deploy log "Preparing Git Reference refs/heads/<branch>" -- if the two don't match, the user needs to change it.

- **Supabase onAuthStateChange SIGNED_OUT FALSE-POSITIVE on page load**: the Supabase `onAuthStateChange` listener can FIRE a SIGNED_OUT event during page load even when the user is actually logged in (session-recovery / token-refresh artifact). If code inside the Layout ties the SIGNED_OUT event to an automatic `window.location.href = '/login'`, this causes an infinite redirect loop or a "jump back to the default page" bug. **Correct pattern**: the SIGNED_OUT event handler should ONLY do localStorage cleanup, NOT auto-redirect. The explicit logout button itself sends the redirect. OR: add the `?next=<window.location.pathname>` parameter to the SIGNED_OUT redirect as well. Plus: for PRs touching auth/session/routing a TEST (preview deploy + browser flow) is mandatory BEFORE you auto-merge.

- **Dashboard session-token != Backend-API auth-token mismatch**: the frontend authenticates with Supabase Auth (`supabase.auth.getSession().access_token`), and sends this as a Bearer token to the backend endpoints. BUT: the backend `authenticate()` function ONLY accepted an api-key and an OAuth token -- it did NOT recognize the Supabase JWT → 401 on every call → `apiFetch` redirect to `/login` (NO `?next=`) → /login fallback to the default page. **Correct fix pattern**: add Supabase JWT validation as the THIRD fallback in the backend `authenticate()` chain. The auth chain: `api_key → OAuth → Supabase JWT → null`. **Debug recipe**: if there is a flash + redirect bug on a dashboard page, FIRST CHECK the backend-API responses in the network tab (status code, response body). If there are 401s → AUTH mismatch between frontend and backend.

- **Bug-fix scope: if 2+ tools / endpoints fail on the same error pattern, fix ALL of them at once**: e.g. two tools of one connector showed the same schema error. The first PR fixed only one, and on the next test the other also failed → second round trip. Pattern: from the bug report text watch for phrases like "does the same", "same error", "on every call" → these are SCOPE markers. In the inter-agent msg, EXPLICITLY instruct: "fix EVERY affected tool in one PR, NOT just the one concrete name given". Plus: if you also fix the error handling (validation-message pass-through), apply it to EVERY tool, not only the current one.

- **Never assume logo asset integration**: if the video agent delivers brand SVGs into its own workspace, that does NOT mean the backend dev agent automatically carries them into the frontend repo's `/public/` folder. You must tell it explicitly, or the orchestrator does it in a separate commit.

- **Verify PID-ENV-leak diagnosis with `tmux list-panes -a`**: if an `ps eww` on an orchestrator-level PID shows an unexpected ENV (e.g. another agent's STATE_DIR), do NOT immediately assume it leaked. First check with the output of `tmux list-panes -a -F "#{session_name} | #{pane_id} | #{pane_pid}"` which session pane the PID belongs to. Lesson: `tmux list-panes -a` takes 1 second, easily built into the initial diagnosis.

- **Heartbeat-blocking IPC stall vs real plugin disconnect**: the Telegram plugin "down" detection runs every minute. The 30-minute heartbeat scheduled task runs for 60-90s, during which the Claude IPC is busy, and the plugin looks `not alive` on a single tick -> the dashboard starts the recovery flow (4 stages, 3-4 minutes downtime). Mitigation: a 120s confirmation threshold: the first negative tick only records suspicion, the second tick escalates. It filters heartbeat stalls, a real outage still triggers recovery within 2 minutes.

- **Claude Code TUI hourly MCP re-handshake (Anthropic side, NOT fixable by us)**: the Claude Code TUI ITSELF restarts the MCP stdio connections automatically every full hour (HH:00:00). The old connection closes cleanly after ~27-52s, the new connection is handled in server.ts with a "stale poller replacement" pattern. This is an ARCHITECTURAL Claude Code feature, there is no CLI flag to turn it off. Mitigation pattern: (1) a soft reconnect with an Up-wraparound flow automatically recovers at Stage 1, (2) Stage-1 disconnect alert in SILENT mode (does not send a Telegram notification, only a warn log on the dashboard). Result: ~30-60s downtime per hour, practically invisible in the UX. Stage 2+ alerts (memory save / session resume / hard restart) ARE LIVE -- those are the truly serious cases.

- **Prompt-design rule: MANDATORY-activity instruction FIRST, conditional silence SECOND**: if a prompt mandates an activity AND allows silence in certain cases, a CONTRADICTORY order is catastrophic. In the heartbeat prompt the no-op tool call rule was put in the MIDDLE, AFTER "Stay silent" -- the orchestrator as an LLM agent chose silence, and I left out the mandatory tool call. Telegram-bun stdio idle → disconnect. **Pattern**: in prompt design the MANDATORY-FIRST rule: when two instructions can be combined (mandatory activity + optional silence), the ACTIVITY instruction goes FIRST, the OPTION SECOND. Plus copy-pasteable examples > abstract description (an LLM agent looks for a pattern first). Own autonomy rule: for every task FIRST do the low-level mandatory step, THEN think.

- **Telegram-bun MCP stdio-stale-on-idle disconnect pattern**: if, as a result of the heartbeat prompt's explicit "Stay silent" / "DO NOT write anything" instruction, the orchestrator agent calls no MCP tool for 30+ minutes, the Telegram plugin bun process stdio pipe is seen as stale and closes. **Diagnostics**: (1) `ps aux | grep "bun.*telegram"` shows the parent claude processes; (2) the `.in_use/` session tracker files; (3) git log for changes to the schedule-runner heartbeat prompt. **Solution**: the heartbeat prompt should REQUIRE the agent to CALL A no-op MCP tool (Read/Bash echo) on every heartbeat -- explicitly NOT a Telegram tool, so the user gets no noise. The no-op tool call generates a stdio flush, which keeps the Telegram-bun pipe alive. **Follow-up**: the 30-minute heartbeat schedule + skipIfBusy=true sometimes generated 16-21 minute gaps, which hit the bun stdio stale threshold. Solution: schedule reduced from 30m → 15m. Pattern: the no-op tool call as keep-alive only works if the max gap < bun stdio stale timeout (~25-30 minutes) -- the interval must be set to 15m with a safe margin. **Differentiation lesson**: if the TIME of the drop falls between HH:00-HH:05, that is NOT idle-stale (heartbeat keep-alive does not help), but the hourly Claude Code TUI MCP re-handshake (separate pattern, see above). Differentiate in diagnosis: (1) keepalive log last keepalive 25+ minutes ago? → idle-stale, reduce heartbeat interval; (2) drop between HH:00-HH:05? → hourly re-handshake, the soft-reconnect's job. Do NOT automatically jump to the heartbeat solution for every disconnect -- FIRST look at the keepalive log. **Regression-diagnosis lesson**: if the user says "this wasn't a problem X days ago", ALWAYS run `git log --since="X+1 days ago" --oneline` first -- the order of recent telegram-monitor / heartbeat / schedule-runner PRs explains the regression a posteriori. Pattern: every agent-quieting change must be carefully measured for side effects on the recovery flow. For quieting PRs a regression test is mandatory: measure the hourly disconnect recovery time over 24h. **/mcp picker viewport scroll pitfall**: `tmux capture-pane`-based text search on the /mcp picker content is MISLEADING, because with 25+ MCPs the picker viewport scrolls and the target entry (Telegram) is NOT visible at the default top. Solution: pre-check dropped, brute-force 1..MAX_UP_ATTEMPTS Up arrow + Enter + verify the "Plugin:telegram:telegram MCP Server" submenu header. On a match it continues to Reconnect, on a miss Escape back to the picker and the next Up. Pattern: in TUI picker automation do not rely on pane-text search if the list can scroll -- a verify step + per-attempt iteration is more reliable. AND: the "Up wraparound" fixed assumption (Telegram=last entry) breaks after ANY new MCP, so brute-force is the more robust default instead of fixed-N navigation. **Validation**: matchedAt=1 in every cycle → recovery <10s. CRITICAL LESSON: `claude mcp list` ≠ /mcp picker order. Pattern: TUI picker order != CLI list order; don't deduce picker position from CLI output, use a brute-force verify loop.

- **Sub-agent API 500 (Anthropic server error) recovery workflow** (a prior incident, backend dev agent task): the sub-agent gets stuck with an "API Error: 500 Internal server error" message. The token count suddenly drops, but the TUI is still running, many background shells are active. This is NOT our fault, it is Anthropic server-side (status.claude.com confirms). **Recovery workflow, user-validated pattern**:
  1. **Esc Esc** into the sub-agent pane → interrupt the current task
  2. **`/compact` + Enter** → compress the conversation history (context refresh)
  3. **Wait 1 hour** (Anthropic incidents typically resolve within 15-60 minutes)
  4. **`WebFetch status.claude.com`** → whether the "Elevated error rates" incident is already resolved
  5. **Restart** the sub-agent task with an inter-agent message
  
  **NOT "postpone to tomorrow"** -- the user's explicit pattern: retry the same day after 1 hour, not the next day. **Save a TODO to memory in the hot tier**: the concrete time + action, tracked between heartbeats.

- **"Request interrupted by user" near a heartbeat window ≠ deliberate user interrupt**: if a Bash command or a longer tool sequence stops with a "Request interrupted by user" message, and this happens close to a heartbeat window (the system reminders come in), do NOT assume the user intervened deliberately. It may be a quirk of the Bash tool's background process, or a limitation of the system reminders framework. **Checking pattern**: before treating such a signal as a "user interrupt", think through: (1) is there a quotable Telegram message containing a user reply? (2) an actual escape/cancel action on the Tool dialog? If NO to both, it is a heartbeat quirk, retry the command.

- **Sub-agent stuck shell + "1 shell still running" TUI block**: the sub-agent Claude Code TUI blocks from accepting new user input if the "1 shell still running" indicator persists -- an earlier background shell NEVER finished. **Diagnostics**: (1) `tmux list-panes -t agent-<name> -F '#{pane_pid}'` → you get a PID (claude.exe), (2) `pgrep -P <pid>` → list of child processes, (3) `ps -o pid,etime,command -p <PID>...` → the zsh shell child with a long ETIME is the culprit. **Solution**: `kill <stuck_shell_pid>`. The Claude TUI then processes the "Background command... failed with exit code 144" message, and frees up the TUI input. **Further pitfall**: if the TUI stays stuck in a "Cooked for Xs" / "Crunched for Xs" animation state even after the kill (5+ minutes), that is a TUI-internal deadlock -- escalate to the user with a request for a Mission Control session restart. State is persistent (memory + kanban + skill in the file system), a restart loses no information.

**Sub-agent restart via dashboard API**:

## Pitfall -- Shape contract in parallel backend+frontend delegation

**Problem**: two agents (backend dev + marketing/frontend) worked in parallel on a new feature (admin page with aggregate stats endpoints and a chart). The backend dev wrote the RPC response in a `{ts: ISO, calls: number}[]` shape, the frontend expected `{label: string, count: number}[]`. Result: the chart was empty (every field `undefined`), the user reported it with a screenshot. A separate PR was needed for the mapping.

**Solution**: when backend + frontend go in parallel with two different agents, the orchestrator-coordinator delegation prompt must give an EXPLICIT JSON shape contract to BOTH parties. E.g.:

> Backend response shape: `{ts: ISO-8601 string, calls: integer}[]`. The frontend accepts THIS shape, do not map it to something else; if the renderer expects other field names, the renderer must be adapted to the shape defined in the backend, not the other way around.

Pattern rule: in the last paragraph of the orchestrator prompt there should be a "**Wire contract** (both agents must use this):" section, listing the key endpoints + their JSON shapes. Written once this takes 30 sec, saves 1-2 fix PRs.

## Pitfall -- Chart.js hardcoded colors on a light theme

**Problem**: the chart-config tick + grid colors were hardcoded `rgba(255,255,255,0.3-0.5)` -- designed for a dark theme. But the user opened it on the light theme, and the labels were invisible.

**Solution**: every Chart.js `ticks.color`, `grid.color`, `tooltip.bodyColor` value should be CSS-var-driven, at runtime with the expression `getComputedStyle(document.documentElement).getPropertyValue('--ink-2').trim()`. Typical variable mapping: `--ink-2` → tick color, `--border` → grid color, `--accent` → primary fill/stroke. Fallback dark-themed value, but the runtime value always wins.

Snippet:
```ts
const css = (name: string, fb: string) => getComputedStyle(document.documentElement).getPropertyValue(name).trim() || fb;
const tickColor = css('--ink-2', 'rgba(0,0,0,0.55)');
const gridColor = css('--border', 'rgba(0,0,0,0.08)');
```

**In the delegation prompt to the frontend agent**: when you ask for chart rendering, write EXPLICITLY that "tick + grid colors CSS-var-driven (`--ink-2`, `--border`), NOT hardcoded".
